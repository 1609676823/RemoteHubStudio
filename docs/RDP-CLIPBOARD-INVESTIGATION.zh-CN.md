# RDP 剪贴板二次勾选问题调查报告

调查日期：2026-09-20。官方资料核对日期：2026-09-20。

本文记录问题原因、排查思路、实际测试过程和结果、微软官方说明，以及尚未证实的事项。文中的签名和信任方案属于已经撤销的实验；当前软件仍使用修改前的连接方式。

## 1. 用户遇到的问题

用户在 RemoteHubStudio 的连接编辑器中开启了“剪贴板”，保存后发起 RDP 连接，Windows“远程桌面连接安全警告”中的剪贴板却默认未勾选，必须手动再次勾选。

初始截图中可见：

- 软件的“剪贴板”开关处于开启状态。
- Windows 提示“未知发布者”。
- Windows 提示列出 WebAuthn 和剪贴板，两项都未勾选。

第一次调整后，用户反馈 WebAuthn 消失，但剪贴板仍未勾选。由此需要分别调查“文件请求了哪些资源”和“Windows 是否授权这些资源”，不能仅以某个选项从界面消失来判断问题解决。

## 2. 原因分析与代码证据

### 2.1 软件中的开关正常传到了 RDP 文件

检查的链路为：连接编辑器 → `RdpOptions.RedirectClipboard` → 连接启动服务 → `RdpFileBuilder` → 临时 `.rdp` 文件 → 外部 `mstsc.exe`。

| 检查位置 | 当时及回退后原始代码的行为 |
| --- | --- |
| `RemoteHubStudio/Domain/RdpOptions.cs` | `RedirectClipboard` 默认值为 `true` |
| `RdpConnectionTypeOptionsPage.LoadFrom` | 将配置值赋给 `_clipboardSwitch.Checked` |
| `RdpConnectionTypeOptionsPage.TryApplyTo` | 将 `_clipboardSwitch.Checked` 写回 `options.RedirectClipboard` |
| `ConnectionLaunchService` | 将当前连接配置传给 `RdpFileBuilder.CreateFile` |
| `RdpFileBuilder.CreateLines` | 根据配置生成 `redirectclipboard:i:1` 或 `redirectclipboard:i:0` |

实际检查和回归测试未发现该链路把开启状态意外重置为关闭。开启时生成的文件已经包含：

```text
redirectclipboard:i:1
```

因此，本次现象的直接原因定位到 Windows 打开 RDP 文件时的资源授权步骤。重复写入同一参数，不能证明系统会自动授权。

### 2.2 Windows 在文件启动流程中增加了资源授权

微软说明，2026 年 4 月安全更新改变了打开 `.rdp` 文件时的提示：文件请求的本地资源默认关闭，需要用户显式选择。其目的与利用恶意 RDP 文件获取本地资源的钓鱼攻击有关。参见[微软安全提示说明，更新于 2026-04-14](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/understanding-security-warnings)。

结合本机测试，可以把过程理解为：软件开关决定文件是否请求剪贴板；Windows 提示决定本次是否授予该资源。软件开关开启而系统提示未勾选，两者可以同时发生。

### 2.3 WebAuthn 是另一个资源选项

实验中增加 `redirectwebauthn:i:0` 后，用户截图中的 WebAuthn 选项消失，但剪贴板仍未勾选。这证明该调整只改变了请求资源列表，不能处理剪贴板的授权问题。回退时也撤销了这项调整。

## 3. 微软官方分别怎么说

以下为官方资料的要点归纳；短引文保留英文原文。资料描述的预期行为与本机观测分别列出，不把文档预期直接当成测试成功。

### 3.1 四月的 Microsoft Learn：资源默认关闭

来源：[Understanding security warnings when opening Remote Desktop (RDP) files](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/understanding-security-warnings)，页面最后更新于 **2026-04-14**。

原文短引：

> “Access to all these resources is off by default”

该页还说明：未签名文件显示未知发布者；签名可使发布者身份得到验证；组织针对特定发布者的策略可能改变体验。直接在远程桌面客户端输入主机名的启动方式，不受此次 RDP 文件提示变更影响。

### 3.2 四月的微软支持团队：签名后可以记住选择

来源：[日本微软 Windows 技术支持团队的 RDP 安全警告说明](https://jpwinsup.github.io/blog/2026/04/24/RemoteDesktopService/RDS/RDPSecurityWarnings/)，发布于 **2026-04-24**。页面明确标注由微软员工发布，内容代表发表时的信息。

文中“可验证发布者”部分及 Q1、Q5 说明：有效签名且证书受信任时，会提供“记住此发布者的远程连接选择”；用户选择资源、勾选记住并连接后，后续同发布者的资源选择可以保留。未签名文件不能通过这一选项记住选择。

该文章 Q2 同时给出“不能完全隐藏安全警告”的答复，并提醒后续更新可能改变行为。本机“一次授权后自动勾选，但确认框仍出现”的结果与其描述相符。

### 3.3 七月的 Microsoft Learn：发布者策略应能自动允许资源

来源：[RDP file security settings in Group Policy](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/manage-rdp-file-security-settings-with-group-policy)，页面最后更新于 **2026-07-14**。

其受信任发布者指纹策略说明包含原文：

> “doesn't display the security warning and automatically enables the redirections”

按该页描述，匹配受信任签名证书时，预期跳过文件安全警告，并启用文件请求的剪贴板、驱动器等资源。该页明确七月更新增加 SHA-2 指纹支持，并建议从旧 SHA-1 指纹迁移到 SHA-256 或更强算法。

**本机没有复现“仅配置当前用户白名单就免提示和自动勾选”的结果。** 具体原因没有查明，详见测试 T07—T09。

### 3.4 如何看待这几份资料的差异

四月支持 FAQ 与七月管理策略文档的日期、讨论侧重点不同，部分表述有差异。较新的策略文档描述了显式发布者信任下的预期例外；不能由此推断“所有 Windows 环境均无需首次授权”，也不能把旧 FAQ 的表述当作不存在任何策略例外的永久结论。

本次采用七月文档作为白名单实验的预期行为，再用实际窗口结果判断实验是否达到预期。官方明确列出的七月变化是 SHA-2 指纹支持，未据此认定免提示机制恰好始于七月。

### 4.1 客户端与测试范围

| 项目 | 记录 |
| --- | --- |
| 程序架构 | WinForms 应用生成临时 RDP 文件，调用外部 mstsc |
| 原生客户端 | `C:\Windows\System32\mstsc.exe`，版本 `10.0.26100.8875` |
| SysWOW64 中的文件 | `C:\Windows\SysWOW64\mstsc.exe`，版本 `10.0.26100.9444` |
| 原生签名工具 | Windows `rdpsign.exe` |
| 测试连接目标 | `127.0.0.1:9`；测试时该端口没有监听服务 |
| 测试凭据 | 生成的样本没有用户名和密码字段内容 |
| 真实服务器 | 未连接用户实际服务器，未验证真实会话中的复制粘贴 |

版本号是本机观测值，不能据此推断其他 Windows 版本的全部行为。系统对话框曾显示当前用户的默认凭据描述；这不代表测试 RDP 文件写入了密码。

### 4.2 三类对照样本

| 当时的样本名 | 剪贴板参数 | WebAuthn 参数 | 签名 | 用途 |
| --- | --- | --- | --- | --- |
| `unsigned-control.rdp` | `redirectclipboard:i:1` | `redirectwebauthn:i:0` | 无 | 重现未知发布者和未授权状态 |
| `signed-clipboard-on.rdp` | `redirectclipboard:i:1` | `redirectwebauthn:i:0` | 专用证书签名 | 检查发布者、白名单和选择记忆 |
| `signed-clipboard-off.rdp` | `redirectclipboard:i:0` | `redirectwebauthn:i:0` | 同一证书签名 | 检查关闭开关是否继续有效 |

签名样本通过应用真实连接计划生成流程创建；生成阶段不启动远程客户端。随后单独通过 mstsc 打开，观察窗口。样本和辅助脚本已在回退时清理，这里保留其参数与结果记录。

## 5. 逐项测试经过、结果与判断

### T01：编辑器、模型和文件生成链路

- **目的：**判断软件是否漏保存或漏写剪贴板设置。
- **做法：**检查编辑器加载/保存代码、配置模型和文件生成逻辑；回归检查分别加载、保存开启和关闭状态，并检查生成内容。
- **结果：**两种状态正确传递，分别得到 `redirectclipboard:i:1`、`redirectclipboard:i:0`。
- **判断：**本次二次勾选现象不能归因于这条配置链路丢失参数。

### T02：显式关闭 WebAuthn

- **做法：**在生成文件中增加 `redirectwebauthn:i:0`，保持剪贴板为开启。
- **结果：**用户后续截图确认 WebAuthn 消失，剪贴板仍未勾选。
- **判断：**请求资源列表发生了变化，剪贴板授权问题仍在。此调整没有作为剪贴板问题的最终解决办法保留。

### T03：签名逻辑和临时文件处理的回归检查

- **做法：**增加可选签名逻辑，检查文件写入并关闭后再交给签名器；模拟签名失败；验证证书选择、有效期、用途和原生工具参数。
- **结果：**剪贴板值、UTF-16 文件编码和目标地址保持正确；模拟失败时临时文件被清理，包括带测试密码保护字段的失败场景。无效签名配置会报错。
- **边界：**这部分包含替身和内存证书测试，不能单独证明真实 Windows 签名或 UI 授权成功。

### T04：当前用户证书和信任配置

- **前提：**用户同意继续进行当前用户专用证书及发布者信任验证。
- **做法：**创建专用 RSA 3072 位、不可导出私钥的代码签名叶证书；只把公钥证书加入当前用户 Root；写入 SHA-256 发布者指纹和应用证书选择。
- **结果：**专用证书有效，代码签名证书链校验通过，Root 中的副本没有私钥，私钥导出策略为不可导出。
- **边界：**证书链有效只能说明信任链检查通过，不能替代资源授权测试。

### T05：真实签名和剪贴板篡改校验

- **做法：**通过原生 `rdpsign` 签署剪贴板开启、关闭两份文件；读取签名范围，核对其中包含 `RedirectClipboard`；对分离式 CMS 签名进行密码学和证书验证。另在内存中翻转已签名的剪贴板值后重新校验。
- **结果：**两份原始签名校验成功，签名证书与应用配置的 SHA-256 相符，摘要算法为 SHA-256；翻转该字段后校验失败。
- **判断：**真实签名有效，而且本次测试的剪贴板字段受签名保护。
- **边界：**RDP 签名有指定范围，此结果不表示文件每个字节或所有参数都受签名保护。

校验过程中曾因没有按 RDP 的分离签名格式构造内容而出现失败；随后依据 `signscope` 字段顺序重建 UTF-16LE 内容并重新验证，取得上述结果。初次格式错误的验证输出没有作为结论依据。

### T06：未签名文件的窗口对照

- **做法：**在保存发布者资源授权之前，打开未签名、剪贴板开启的回环样本。
- **结果：**出现橙色未知发布者提示，剪贴板未勾选，与用户最初问题一致。
- **判断：**即使生成文件明确开启剪贴板，未签名文件的系统授权仍会默认关闭该资源。

### T07：签名文件加 SHA-256 发布者白名单

- **做法：**在证书受信任、当前用户发布者策略包含 `sha256:<证书指纹>` 的条件下，打开剪贴板开启的签名样本。
- **预期：**按七月策略文档，匹配发布者后跳过警告并启用请求资源。
- **结果：**窗口改为黄色的发布者确认，显示 `RemoteHubStudio RDP File Signing`，出现“记住我对此发布者远程连接的选择”；但窗口仍出现，剪贴板依旧未勾选。
- **判断：**签名发布者被识别，白名单实验没有达到免提示和自动勾选的预期。不能把“已写入策略”表述为“客户端已采用策略”。

### T08：同一证书追加旧式 SHA-1 标识作对照

- **做法：**临时在同一个当前用户白名单值中追加同证书的旧式指纹，再用新的客户端进程打开开启剪贴板的签名文件。
- **结果：**仍显示发布者确认，剪贴板未勾选；对照结束后恢复为原来的 SHA-256 条目。
- **判断：**本次追加旧式标识没有改善现象，无法据此认定是 SHA-256 格式导致，也没有保留 SHA-1 作为修复。

### T09：策略位置、注册表视图与模板检查

- **做法：**只读检查相关 HKCU/HKLM 策略位置、32/64 位视图及本机 ADMX/ADML 说明，核对指纹前缀、值类型和实际字符串；查阅微软策略说明。
- **结果：**相关用户值一致，未发现已配置的相关机器策略覆盖；模板中有 SHA-2 指纹说明。未找到必须额外设置 `EnableTrustedRdpFiles` 的可靠依据，也没有添加该猜测值。
- **判断：**没有定位到一个已证实的配置遗漏。白名单未达到预期的具体原因仍未查明。
- **边界：**不能把这个结果外推为 HKCU 策略普遍无效、所有 SHA-2 指纹都不支持，或直接归因于注册表位数。

### T10：原生与 SysWOW64 启动路径检查

- **做法：**检查两处 mstsc 文件版本，尝试从 SysWOW64 启动测试快捷方式，再读取实际进程路径。
- **结果：**该次启动最终转交给 `System32\mstsc.exe`。另外确认 32 位程序访问原生签名工具时需要正确处理系统目录重定向。
- **判断：**这次尝试没有形成独立的 32 位 mstsc 行为对照；两个文件版本不同，也不足以证明授权现象由位数导致。

32 位进程可通过 `Sysnative` 访问原生系统目录，是微软[文件系统重定向说明](https://learn.microsoft.com/en-us/windows/win32/winprog64/file-system-redirector)记录的机制。它解释工具路径问题，不构成剪贴板授权原因的证明。

### T11：用户勾选剪贴板并记住发布者选择

- **做法：**打开已签名的回环样本。用户手动勾选“剪贴板”和“记住我对此发布者远程连接的选择”，再点击连接。
- **结果：**用户确认完成；Windows 为该专用发布者保存了 `PublisherPermissions` 记录，其中 `Clipboard` 为 DWORD `1`。
- **边界：**回环端口没有远程服务，连接失败属于预期；这一步验证的是授权保存，不是真实远程登录。

### T12：退出客户端后重新打开同一签名连接

- **做法：**结束此次测试客户端，重新打开同一发布者签名、剪贴板开启的样本。
- **结果：**新的系统提示中，剪贴板自动处于勾选状态；发布者确认框仍然出现。
- **判断：**本机已验证“完成一次资源授权后，后续无需重新勾选剪贴板”。没有验证或宣称“所有安全提示都消失”。

### T13：记住授权后，打开关闭剪贴板的签名文件

- **做法：**打开同证书签名、`redirectclipboard:i:0` 的对照样本。
- **结果：**Windows 的资源列表中不再列出剪贴板。
- **判断：**在文件和窗口层面，关闭资源请求的开关仍生效，已记住的授权没有使这个测试文件重新请求剪贴板。

### T14：构建、回归和撤销验证

- **结果：**实验阶段的签名回归、配置脚本内存替身测试和真实签名探针通过。用户决定撤销后，代码恢复原状，Debug/Release 构建均为 0 警告、0 错误；原有连接启动回归通过。
- **当时的检查标识：**`RDP_FILE_SIGNING_TESTS_OK`、`RDP_SIGNING_SETUP_TESTS_OK`、`RDP_SIGNING_LIVE_PROBE_OK`；回退后为 `CONNECTION_LAUNCH_CANCELLATION_OK`。
- **边界：**上述标识分别覆盖代码、脚本或签名测试，不能替代窗口观察及真实远程会话测试。实验测试代码已随修复撤销。

## 6. 签名实验实际改动过哪些 Windows 状态

此节记录历史范围，便于以后核对；当前这些实验状态已清理。

| 位置 | 当时的用途 |
| --- | --- |
| `CurrentUser\My` | 保存专用签名证书及不可导出私钥 |
| `CurrentUser\Root` | 保存该证书的公钥副本，用于证书链信任 |
| `HKCU\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services\TrustedCertThumbprints`（值） | 追加专用证书 SHA-256 发布者标识 |
| `HKCU\Software\RemoteHubStudio\RdpFileSigning` | 保存应用签名证书选择和脚本撤销记录 |
| `HKCU\Software\Microsoft\Terminal Server Client\PublisherPermissions\<证书 SHA-256>00` | Windows 在用户手动授权后保存 `Clipboard=1` |

专用发布者：`RemoteHubStudio RDP File Signing`。专用证书 SHA-256：`DE0CE572BC1D9B026A8C136F12E100E349D2B58B586AC0B786C2AF14213F5912`。

## 8. 不修改 Windows 设置的方案分析（未实施）

约束为不安装额外信任证书、不写策略或授权注册表、不预存 Windows 凭据、不改共享 `Default.rdp`，同时尽量保留现有逐连接设置。

| 方案 | 分析与代价 | 本次取舍 |
| --- | --- | --- |
| 保留外部 mstsc + 动态 RDP 文件 | 未找到微软公开支持的仅靠文件属性自动同意剪贴板的方法 | 接受系统提示中的手动勾选 |
| 只使用 `mstsc /v:主机:端口` | 是不同的启动流程；公开命令行无法等价承载现有用户名、密码和全部资源选项。依赖默认配置会失去逐连接控制 | 未改成简化模式 |
| 内嵌 RDP ActiveX 控件 | 官方提供实例级提示控制和剪贴板属性；需增加会话宿主、COM 生命周期、焦点快捷键、多屏全屏、错误重连等处理 | 有技术路径，但属于架构改造 |
| 更换 RDP 客户端 | 需要新的依赖、配置映射、凭据处理和兼容性测试 | 未实施 |
| 公共可信证书给动态 RDP 签名 | 仍需逐文件签名、私钥管理和首次资源授权评估；只给 EXE 签名不等于 RDP 文件已签名 | 不为当前轻微问题引入 |

此处的成本和适用性属于工程判断。可以继续研究应用内方案，但没有找到兼顾现有功能、改动很小且完全不触碰 Windows 配置的直接修复。
